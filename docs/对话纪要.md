# 对话纪要 · 选题准备阶段

记录时间：2026-09-22 至 2026-09-24
记录内容：选题从零到「环境就绪、基线数据就位、汇报材料成稿」的全过程

---

## 一、起点：一堆来自 macOS 的资料

桌面上有一个 `PMUX选题资料.zip`，从 Mac 拷来的。在 Windows 上打开是乱码。
原因是这个包没设置 ZIP 的 UTF-8 文件名标志位，Windows 按 GBK 解码中文名，
另外还夹带了 `__MACOSX/` 资源分叉和 `.DS_Store`。

处理方式：重建成标准 ZIP（置 UTF-8 标志位、剔除 21 个 Mac 杂项条目），
并用 CRC 逐一比对确认内容零改动，然后解进项目、建了本地 git 仓库。

## 二、搞清楚这个选题到底要做什么

读了官方选题指南和资料包，结论是：

- 要做的是**给 Yosys 加一条命令**，不是设计电路。属于 EDA 工具开发，不需要硬件平台。
- 难点不在「换一种实现」，而在**判断控制信号的性质**（互斥、one-hot、无关项）。
- 评分里面积占 40 分（20% 满分线），效率占 30 分，两者几乎同等重要。
- **等价验证是生死线**：任一用例不等价，功能性 0 分且其余不计分。

## 三、环境：从零搭起，并发现「能跑不能改」

装好 OSS CAD Suite（含 Yosys、EQY、SBY、z3/yices/boolector、iverilog），
又装了厂商工具 eLinx 3.0.7 教育版。

关键发现：**这套环境能跑、能测、能验证，但改不了**。
Yosys 官方只正式支持 Linux 和 macOS，Windows 原生构建不在支持范围；
现成的二进制包既没有编译链，也不提供链接所需的库文件。要写 C++ pass 必须换平台。

这也直接决定了团队分工的思路：一个人有 Mac、两个人只有 Windows，
所以需要一台共享的构建环境（Linux 服务器或 WSL2）。

## 四、第一个实质性发现：`$pmux` 不是随便写就有的

第一版测试用例用 `case (1'b1)` 配位选条件写，跑 Yosys 发现根本不生成 `$pmux`。
于是写了 5 种候选写法做对照实验，才确认只有 `case (sel)` 这种
「选择信号对常量分支逐一比较」的写法才会生成。

后来还澄清了一件容易搞错的事：位选条件写法和 `$pmux` 的**语义不同**
（前者是多根独立使能线、可同时有效），不能直接比单元数。
这个错误一度写进了汇报文档，后来复核发现并修正。

## 五、量化空间：从 132 到 56

用 8 位宽、8 选 1 的用例测出：

- 默认综合流程：132 个门
- 额外调用一步现成的展平：103 个门（缩减 22%）
- 等价功能的显式选择树：56 个门（缩减 58%）

结论是**空间确实存在**，而且现成工具只拿走了小部分，大头要留给自研算法。
这排除了选题最大的风险，也就是「万一没空间可做」。

## 六、等价验证跑通，并证明了它真的有用

用两个用例做了演示：正确的重构实现被求解器通过归纳法证明等价；
故意把两个数据输入调换的版本被找出反例，还导出了可复现的波形。

顺带踩了个坑：`.eqy` 配置里写中文注释会触发 GBK 解码错误，需要设 `PYTHONUTF8=1`。

## 七、组委会要求 Yosys 0.68，全部数据重测

此前数据是 0.69 测的。按 tag 日期（v0.68 发布于 2026-08-05）定位到 8 月上旬的
OSS CAD Suite 构建，装好 0.68+27 并把它设为主用版本。

重测发现两处差异：展平后 103（0.68）对 88（0.69），`pmux_nested` 112 对 106。
核心结论（132 与 56）跨版本稳定。结论是**版本必须锁死**。
