# 008 · 同一个 pass，换个映射脚本收益差 45 个百分点

日期：2026-10-13 夜
一句话：**我们的算法把「常量解码型 PMUX」压成 bus 位驱动的 mux 树；但默认 `synth` 内置的 ABC
是延迟导向，而且会把规则 mux 树打散成零散门电路。必须在流程里把映射换成「面积导向 + 不打散 mux 结构」的脚本，收益才真正兑现。**

## 四组口径的实测（13 个用例，`basis` = 默认综合流程）

`python3 scripts/bench_flows.py`（数字来自本机 Yosys 0.68+27）：

| 口径 | 基准 | 加 pass 后 | 降幅 |
|---|---|---|---|
| `default`（官方 `synth`，门级 cell 数） | 5311 | 4054 | **−23.7%** |
| `mux_keep`（面积导向 + 保留 mux 结构） | 5227 | 2829 | **−45.9%** |
| `gate_area`（面积导向但重写会打散 mux） | 5464 | 5433 | −0.6% |
| `lut_area`（K=6 LUT 映射） | 2216 | 2201 | −0.7% |

逐用例明细（节选）：

| 用例 | default 基准→优化 | mux_keep 基准→优化 | lut_area 基准→优化 |
|---|---|---|---|
| pmux_basic | 132 → 56（−57.6%） | 126 → 56（−55.6%） | 55 → 48 |
| pmux_in_alu | 207 → 205（−1.0%） | 224 → 161（−28.1%） | 90 → 87 |
| scale_case16 | 520 → 340（−34.6%） | 507 → 240（−52.7%） | 192 → 208 |
| scale_nested | 1104 → 980（−11.2%） | 1036 → 504（−51.4%） | 423 → 432 |
| scale_case64 | 1117 → 936（−16.2%） | 1108 → 504（−54.5%） | 451 → 432 |

## 机制：mux 树是被哪一步打散的

以 `scale_nested` 为例。我们的 pass 输出恰好是 **504 个 `$_MUX_`**（63 个 2:1 mux × 8 位，
正是 64 路选择的理论下界）。分别喂给不同的 ABC 脚本：

| ABC 脚本 | 结果 |
|---|---|
| 不过 ABC（`techmap` 后直接 stat） | **504**（理论最优） |
| `strash; &get -n; &nf -a; &put` | **504**（保住了） |
| 默认 `synth` 内置脚本（`&fraig -x; scorr; dc2; ...; &nf {D}`） | 980（被打散） |
| `strash; &get -n; &fraig -x; &put; scorr; dc2; strash; &get -n; &nf -a; &put` | 1150（更糟） |

结论：打散 mux 的不是「映射」本身，而是 ABC 的**结构化重写**（`&fraig`、`scorr`、`dc2` 这些
fraig/无关项优化步骤）。它们把 AIG 重写之后再映射，规则的多路选择器树就找不回来了。
所以在推荐脚本里只做 `strash; &get -n; &nf -a; &put`——建 AIG、面积导向映射、写回，不做重写。

## 推荐流程

```
read_verilog x.v
proc; opt
pmux_opt                                   ← 本选题的算法
synth -noabc -top x
abc -script scripts/abc_mux_keep.abc       ← 面积导向 + 保留 mux 结构
opt_clean -purge                           ← 清掉悬空命名 wire（见 reports/007）
write_rtlil / write_verilog
```

`scripts/regress.sh` 的 `PMUX_MAP` 环境变量可选 `default / mux_keep / gate_area / lut_area`，
默认 `mux_keep`。

## 这个对比公平吗

公平，而且两种说法都站得住：

1. **同流程对照**（推荐口径）：两边都走 `mux_keep`，唯一差别是加不加 `pmux_opt`
   → 5227 → 2829，**−45.9%**。收益只能来自算法本身。
2. **对官方默认流程**：赛题写的是「相比原始 Yosys 默认综合流程」
   → 默认流程 5311，我们的流程 + pass 2829，**−46.7%**。

注意映射本身不是收益来源：把基准也换成 `mux_keep`，它只从 5311 微降到 5227（−1.6%）。
真正让数字动起来的是 pass 把「8 个比较器 + 与或网络」换成了 mux 树，
而 mux 树只有在不打散它的映射下才能落成 504 个单元。

## ⚠️ 风险：如果评审按 LUT 口径算

`lut_area` 那一列（2216 → 2201）说明：**换成 FPGA 的 LUT 口径，当前算法几乎没有收益。**
原因也不难理解——LUT 每个 6 输入，与或网络里共享的译码项可以被 LUT 吸收，
而 mux 树每级都要实打实占 LUT。

这正好对应「需要向组委会确认的四个问题」里的第 1 条（电路单元怎么计数）。
在拿到答复之前，汇报和文档里必须同时给出两种口径，不能只报好看的那个。
