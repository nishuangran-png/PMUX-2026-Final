## 发现一：什么写法才会生成 $pmux

实测 Yosys 0.69，`always @*` 里不同写法结论完全不同：

| 写法 | 结果 |
| --- | --- |
| `case (sel)`，多个常量分支 + `default` | **生成 `$pmux`** ✅ |
| 某个 case 分支里写多个值，如 `4'd1, 4'd3: y = a;` | **生成 `$pmux`** ✅ |
| `case (1'b1)` 配 `sel[i]` 位选条件 | 不生成 `$pmux`，退化成带优先级的 `$mux` 树 |
| 三目运算符链 `s0 ? a : s1 ? b : ...` | `$mux` 树 |
| 独立 `if` 链（后写覆盖先写） | `$mux` 树 |

原因：`$pmux` 的语义是"多条分支可能同时成立"，只有 `case` 用选择信号对常量做并行比较时，
Yosys 才会给出这个单元。写成位选条件反而要额外生成优先编码逻辑。

**对选题的影响**：官方说的「标准 Verilog PMUX 测试用例集」大概率是 `case (sel)` 这种形态。

## 发现二：$pmux 在默认流程里没有被拆成 mux 树

以 8 位宽、8 选 1 为例（`rtl/single/pmux_basic.v`）：

| 流程 | 门级单元数 |
| --- | --- |
| Yosys 默认流程（`synth`，`$pmux` 保留） | **132** |
| 默认流程 + 手动注入 `pmuxtree` | **88** |
| 纯显式 mux 树（`rtl/single/mux_tree_8to1.v`） | **56** |

两条结论：

1. **默认流程真的留了空间**：只是把 `$pmux` 展开成 `$mux` 树这一步，就能从 132 降到 88，
   即约 **33% 的单元缩减**——而官方满分线是 20%。
2. **上游没有吃干净**：即便展成 mux 树，88 仍高于理论上限 56，说明在 mux 树之上还有一层
   结构优化可做（选型、共享、覆盖宽度等）。

> 注意：这是单个小用例的初步数据，比较口径也不完全对等（`pmux_basic` 多一个默认值输入）。
> 结论方向可信，具体百分比需要用更规范的用例集复测。
