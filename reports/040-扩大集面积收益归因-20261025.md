# 040 · 扩大集面积收益归因（2026-10-25）

## 1. 结论

扩大集总面积不是“普遍每例只降一点”，而是 33/35 个用例完全持平，只有 2 个小用例各下降
25%。因此总缩减率被大用例的零变化稀释了：

- 合计：`3439 → 3430`，只减少 9 个逻辑单元，面积加权缩减率 `0.26%`；
- 35 例等权平均单例缩减率：`1.43%`；
- 改善 2 例、持平 33 例、回退 0 例；
- 最大的 6 个用例占基线面积 `3014/3439 = 87.64%`，全部为 0 变化。

这两个百分比都不能和官方四题的 `32.05%` 直接比较。官方四题是专门用于本赛题的 PMUX
基准；本次 35 例是 Yosys 上游 RTL 功能测试集，其中大量面积来自存储器、算术共享或
大规模常量 `case`，并不是可折叠的优先 MUX 链。

## 2. 面积为什么被稀释

| 用例 | 基线面积 | 占总面积 | 变化 | 进入 pass 时的主要结构 |
|---|---:|---:|---:|---|
| `wide_thru_priority__test` | 1123 | 32.65% | 0 | 多写口存储器；0 个 `$pmux`、8 个 `$mux`，最终 512 个 DFF |
| `case_large__case_lage_top` | 638 | 18.55% | 0 | 1 个 256 路 `$pmux`、256 个 `$eq`；选择总线宽 128 位 |
| `opt_share_large_pmux_cat_multipart` | 426 | 12.39% | 0 | 1 个 `$pmux`，分支是加减法组合，不是成对共享 PMUX |
| `opt_share_large_pmux_multipart` | 311 | 9.04% | 0 | 同上 |
| `opt_share_large_pmux_cat` | 271 | 7.88% | 0 | 同上 |
| `opt_share_large_pmux_part` | 245 | 7.12% | 0 | 同上 |
| `test_simulation_mux__f5_test` | 80 | 2.33% | 0 | 64 路 one-hot 解码，选择数据为 64 位 `in`，不是选择位重排 |
| `muxpack__mux_case_unbal_8_7` | 57 | 1.66% | 0 | 2 个 `$pmux`，数据来自 56 位输入总线，未满足稀疏折叠条件 |

前 6 个用例合计占 87.64% 的面积，已经足以解释总面积指标为什么低。它们是“面积大户”，
但并不是当前 `pmux_opt` 的目标结构。

## 3. 实测的跳过原因

使用候选版 Yosys `0.69+post`（commit `9f75ca1f9834…`）在 `synth_intel` coarse 阶段
等价位置执行 `pmux_opt -v`，结果如下。

### 3.1 `wide_thru_priority`

进入 pass 时是 `0 $pmux / 8 $mux / 3 $memwr_v2 / 1 $memrd`，最终 512 个 DFF。它不是
PMUX 结构，面积主要是存储器写入逻辑和寄存器；当前任何 PMUX 规则都没有可匹配对象。

### 3.2 `case_large`

进入 pass 时是 `1 $pmux / 256 $eq / 0 $mux`。报告汇总为：

```text
pmux_opt: 1 $pmux cell(s), merged 0 pair(s), skipped 1, lowered 0 constant ROM(s).
```

该 256 路 PMUX 的选择位来自 128 位常量的完整等值比较。当前双 PMUX 规则只接受
`2..8` 位解码总线；同时只有一个 PMUX，也没有可配对对象。因此这次被保守跳过。
这是一个后续可以单独研究的“宽常量解码”方向，但现有实验没有证明改写后不会回退。

### 3.3 四个 `opt_share_large_pmux_*`

每个用例进入 pass 时都恰好只有 1 个 `$pmux`，且选择码覆盖 `sel=0..6`。当前双 PMUX
规则要求存在第二个同选择网络、数据按最低位成对交换的 PMUX，因此没有 partner。

稀疏局部折叠路径也尝试过：它们能看到 `A=x`。其中 32 位输出的
`opt_share_large_pmux_cat` 和 `opt_share_large_pmux_cat_multipart` 超过该路径的
16 位输出上限，直接退出；16 位输出的 `multipart` 和 `part` 虽然通过位宽门槛，但数据
分支是 `a+b`、`a-b`、`b-c` 等算术结果，输出位不能由 `sel` 总线位直接重排得到，日志出现：

```text
no direct bus bit for output bit 0
```

所以这四例同时错过“双 PMUX 共享”和“选择位重排折叠”两条路径。它们本来就是上游用于
测试 `opt_share` 的算术共享用例，不应作为当前 PMUX 算法的收益预期。

### 3.4 `test_simulation_mux__f5_test`

这是 64 选 1 的数据 MUX：`out = in[select]`。日志中的 `bus=select` 是选择信号，
而数据叶子是 `in[63:0]` 的不同位；当前规则试图证明输出等于选择总线位的重排，因此
`no direct bus bit` 正确拒绝。它不是 `pmux_opt` 已覆盖的“常量解码型局部更新”。

### 3.5 `muxpack__mux_case_unbal_8_7`

进入 pass 时有 2 个 `$pmux`，但 `merged=0`、`collapsed=0`。两例的稀疏候选都因数据
来自 56 位输入总线、无法由 3 位 `s` 直接重排而未被折叠；面积 57 保持不变。

## 4. 为什么只有两个小用例下降

只有 `muxpack__mux_if_unbal_5_3_order` 和
`muxpack__mux_if_unbal_5_3_nonexcl` 的乱序/非互斥优先链进入了自适应链折叠路径：

```text
20 → 15（25.00%）
16 → 12（25.00%）
```

这两例合计只减少 9 个逻辑单元，而小用例集合本身的总面积只有 425；即使对小用例表现不错，
也无法抵消前 6 个用例的零变化。规范、密集、降序优先链则被有意留给 ABC9，避免提前分组
造成映射回退。

## 5. 正确的评价口径

- 官方成绩：只看四个公开用例，当前为 `288→202`、`25→16`、`13→9`、`38→26`，平均
  `32.05%`，四题 EQY PASS；
- 扩大集：只看作“35 个真实 RTL 顶层不回归”的证据，不把 `0.26%` 写成失败，也不把
  `1.43%` 写成官方成绩；
- 更合理的泛化指标：按结构分层统计命中率、PMUX 目标面积缩减和回退率，而不是把存储器、
  算术共享和常量 `case` 全部塞进同一个总面积分母。

## 6. 后续优先级

1. 为 35 例建立结构分层：`$pmux` 链、one-hot 解码、双 PMUX、存储器、算术共享、无 MUX；
2. 优先研究 `case_large` 的宽常量解码，这是唯一占面积很大且明确包含 PMUX 的未命中用例；
3. `f5_test` 的 64 选 1 可作为 one-hot 解码共享候选，但其总面积上限只有 80，不能期待它
   改变整体加权结论；
4. `wide_thru_priority` 和 `opt_share_*` 不应被当成当前 PMUX 算法的主要考核项；
5. 任何改写都必须重新跑官方四题、35 例 EQY、面积和效率，不以单个上游用例的收益换取回退。
