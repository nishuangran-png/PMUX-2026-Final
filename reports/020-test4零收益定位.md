# 020 · test4 零收益定位：ROM 化发生在 PMUX 优化之前

日期：2026-10-22  
基线：Yosys 官网 `v0.69`，commit `9f75ca1f9834a39a863915b5dae0c7b1e33533bc`  
结论：`test4` 的 `0.00%` 是当前 pass 的覆盖缺口，不是面积统计错误，也不能解释为
`test4` 已经优化到极限。

## 一、直接结论

`test4` 的优化版和原版最终都是：

| 项目 | 原版 | 优化版 |
|---|---:|---:|
| `cycloneiv_lcell_comb` | 37 | 37 |
| `$not` | 1 | 1 |
| 面积口径 `lcell + $not` | 38 | 38 |
| `dffeas` | 10 | 10 |
| 缩减率 |  | **0.00%** |

原版和优化版在 ABC9 之后结构一致且 EQY `PASS`。差异不是“做了改写又回退”，而是
`pmux_opt` 在 `test4` 上没有发生任何改写。

网表级复核也一致：两份 `write_json` 结果仅包含构建目录路径差异；把
`official-v069-opt` 归一化为 `official-v069` 后，两份网表 SHA-256 均为
`abb41ae901baaeec078f1dda6ca28673550dc64f1335fc8cb6620ef49a5664a4`。

### 统计口径更正（2026-10-22）

队友当前反馈的 test4 结果是 **基线 36、优化后仍为 36**，没有面积收益。其拆分为
`33 cycloneiv_lcell_comb + 3 $not = 36`；这是 Intel 逻辑单元口径，不是通用 `$lut`
口径。此前把该结果写成 `38 → 36`、说成“减少两个 LUT”，或用通用 4-LUT 的 36 来解释，
都不准确，已撤回。

本机当前基线构建得到 `37 LCELL + 1 $not = 38`，所以绝对数值与队友的 36 不同。这说明
两边的 Yosys/ABC9 构建或映射结果存在差异，不能把 36 和 38 直接混算；但两边共同结论仍是
优化前后不变。要确认队友的 `33 + 3` 是否可在同一环境下复现，必须以其原始
`stat -width`、`yosys -V`、`yosys-abc -c version` 和完整综合命令为准。

## 二、RTL 本身是什么结构

`rtl/official/test4/test4.v:47-80` 是一个覆盖全部 32 个输入码的常量 `case`：

```verilog
case (datain)              // datain 为 5 bit
    5'd0:  {dataout, only_5b, datain_5bis7, data_dp, data_dn} <= 10'b...;
    ...
    5'd31: {dataout, only_5b, datain_5bis7, data_dp, data_dn} <= 10'b...;
endcase
```

这 32 个分支有三个关键性质：

1. 每个分支的右值都是常量；
2. 所有分支更新同一个 10 bit 赋值目标；
3. 32 个值完整覆盖 5 bit 输入空间，没有嵌套 `switch`。

因此它语义上就是一张 `32 × 10` 的常量查找表，而不是一组需要共享选择网络的普通 PMUX。

## 三、Yosys 的 pass 顺序是根因

`proc` 内部先执行 `proc_rom`，再执行 `proc_mux`：

- `tools/build/official-v069/passes/proc/proc.cc:128-131`

`proc_rom` 的转换条件位于：

- `tools/build/official-v069/passes/proc/proc_rom.cc:50-56`
- `tools/build/official-v069/passes/proc/proc_rom.cc:143-151`

`test4` 恰好满足全部条件。默认综合日志明确记录：

```text
2.5.6. Executing PROC_ROM pass (convert switches to ROMs).
Converted 1 switch.
```

执行完 `proc` 后，该模块包含 `1 memories / 320 memory bits`，而这部分电路对应
`$mem_v2`、`$memrd_v2`、`$meminit`，没有对应的大型 `$pmux`：

```text
1 memories
320 memory bits
1   $meminit
1   $memrd_v2
```

集成点在 `synth_intel` 的 coarse 阶段：

- `tools/build/official-v069-opt/techlibs/intel/synth_intel.cc:209-213`

`pmux_opt` 到达时只能看到已经被 `proc_rom` 替换后的 ROM，日志为：

```text
2.16. Executing PMUX_OPT pass.
pmux_opt: 0 $pmux cell(s), merged 0 pair(s), skipped 0.
```

所以这里的 `0` 首先表示“**没有可处理的 PMUX**”，而不是“候选改写收益为 0”。

## 四、为什么最终仍是 37 个 LCELL

默认流程随后尝试把该只读 ROM 映射到 M9K，但它是组合读，读地址和读数据都没有同步寄存器：

```text
Checking read port ...: no output FF found.
Checking read port address ...: no address FF found.
```

因此 `memory_bram` 不能把它装进 M9K。后面的 `memory_map` 把常量 ROM 展开为组合选择树：

```text
Mapping memory $auto$proc_rom.cc:155:do_switch$8 in module \test4:
  created 32 $dff cells and 0 static cells of width 10.
  read interface: 0 $dff and 31 $mux cells.
```

中间的常量 DFF 随后被常量传播和优化删除，最终剩 10 个真实输出寄存器。组合部分是
31 个 `$mux` 组成的常量选择树，再交给 ABC9 映射。原版和优化版走的是完全相同的后半段，
所以都得到 `37 LCELL + 1 $not + 10 DFF = 38` 的面积口径。

`test4` 的组合输入必须在同一个时钟沿前得到结果，不能为了使用 M9K 而私自增加一拍读延迟，
否则会改变模块接口语义。因此这里的同步 BRAM 不可用是正常结果。

## 五、关掉 `proc_rom` 也不是解法

对照命令：

```bash
tools/build/official-v069-opt/build/yosys -p \
  'read_verilog rtl/official/test4/test4.v; proc -norom; synth_intel -family cycloneiv -top test4; stat'
```

禁止 ROM 化后，`pmux_opt` 才看到 3 个 `$pmux`，但当前规则仍没有匹配：

```text
pmux_opt: 3 $pmux cell(s), merged 0 pair(s), skipped 1.
```

`-v` 日志进一步显示：其中一项是完整的 32 路常量选择，选择码为 `1f ... 00`；其余两项含
未定义基值，选择位也不是当前规则要求的常量译码。它们既不是可成对交换的 dual-PMUX，也
不是当前规则支持的稀疏局部更新结构。

更关键的是最终面积反而恶化：

| 流程 | `cycloneiv_lcell_comb` | `$not` | 面积口径 |
|---|---:|---:|---:|
| 默认 `proc_rom` | 37 | 1 | **38** |
| `proc -norom` | 64 | 1 | **65** |

因此不能通过全局关闭 `proc_rom` 来“修复” `test4`；这会把原本更紧凑的常量 ROM 展开成更大的
组合逻辑，并可能影响其他用例。

## 六、对老师和汇报的准确表述

建议使用下面的口径：

> `test4` 的 0% 不是优化后性能回退，也不是面积统计错误。Yosys 默认 `proc` 会在
> `proc_mux` 之前执行 `proc_rom`，把这个 32 路常量 `case` 转换成 32×10 的只读 ROM。
> 我们的 `pmux_opt` 位于 `proc` 之后，在该用例日志中实际看到 0 个 `$pmux`，所以没有
> 命中改写规则。之后 ROM 因组合读无法映射到 M9K，被 `memory_map` 展开成 31 个 mux 的
> 常量选择树，再由 ABC9 映射成 37 个 LCELL。原版与优化版后半段完全相同，因此都是 38，
> 缩减率为 0。这个结果说明当前算法尚未覆盖“常量 ROM”这一形态，不代表 `test4` 已经没有
> 优化空间；强行关闭 `proc_rom` 反而会从 38 恶化到 65。

## 七、后续可选方向

1. 在 `memory_map` 之前识别带初值的只读 `$mem_v2`，为常量查找表建立独立的成本模型。
2. 在 `memory_map` 之后研究 31 个 mux 组成的常量选择树与 ABC9 的协同，而不是直接关闭
   `proc_rom`。
3. 任何新规则都必须同时满足：LCELL 严格下降、DFF 不增加、EQY 通过、时间与峰值内存不超过
   原版 `1.05` 倍。
4. 当前优先级仍应放在隐藏效率用例和泛化回归；不能为了 `test4` 引入只识别固定 5 bit、
   固定 32 分支或固定信号名的特判。

## 八、阶段修复与冻结结果（2026-10-23）

在上述定位完成后，新增了一条不依赖用例名和固定位宽的通用规则：

1. 识别无写口、全初始化、异步组合读、地址空间为 2 的幂的小型常量 ROM；
2. 将每个输出位转换为 `$lut` 真值表，绕开 `memory_map` 先生成 31 个 `$mux` 的路径；
3. 若 ROM 输出仅被一个“常量基值 vs ROM”的 `$mux` 使用，则吸收该 mux，把选择位并入
   LUT 输入；`test4` 中对应的是 10 位输出与 `ena` 常量清零。

当前实测：

| 用例 | 基线 `lcell + $not` | 优化后 | 缩减率 | DFF | EQY |
|---|---:|---:|---:|---:|:---:|
| test1 | 288 | 202 | 29.86% | 222 | PASS |
| test2 | 25 | 16 | 36.00% | 0 | PASS |
| test3 | 13 | 10 | 23.08% | 17 | PASS |
| test4 | 38 | 35 | 7.89% | 10 | PASS |
| **平均** |  |  | **24.21%** |  |  |

效率采样中最大墙钟比为 `1.000`，最大峰值 RSS 比为 `1.018`，仍在四题 `1.05` 门槛内。

### 归因边界

当前 `test4` 收益不能全部归因于 PMUX/ROM 算法。手工控制实验显示，ABC9 输入顺序也会
显著改变 LCELL 数：

| 流程 | test4 `LCELL + $not` |
|---|---:|
| 官方基线，默认 | 38 |
| 官方基线，仅 `sort` | 35 |
| 官方基线，`autoname; sort` | 36 |
| 优化版，默认 | 38 |
| 优化版，仅 `sort` | 36 |
| 优化版，`autoname; sort` | 35 |

因此本阶段只冻结以下结论：

- 零收益根因已经确认；
- 常量 ROM 转 LUT 的路径可以打通，并保持 EQY 通过；
- 当前构建在固定复现命令下得到 `38 → 35`；
- ABC9 结果对输入顺序敏感，尚不能宣称该缩减可稳定泛化；
- 若赛题只允许提交独立 pass、不允许修改 `synth_intel.cc` 的 ABC9 调用顺序，则
  `autoname; sort` 不能计入算法收益，需要重新测量纯规则版本。
