# Yosys 上游现有的 mux 优化机制

这些 `.cc` 文件取自 Yosys 官方仓库（https://github.com/YosysHQ/yosys）的 `main` 分支。它们是目前 Yosys 里和 mux / PMUX 优化直接相关的 pass 源码。

**为什么要把它们放在这里：** 赛题要求「在 Yosys 框架内新增自定义 Tcl 命令」实现 PMUX 优化，目标是「相比原始 Yosys 默认综合流程缩减 10%」。也就是说，你的算法必须在下面这些已有 pass 都没处理好的结构上做出增量。先读懂它们做了什么，才能知道剩下的空间在哪。

## 文件对照

### `pmux2shiftx.cc`
官方说明：`pmux2shiftx [options] [selection]` — This pass transforms `$pmux` cells to `$shiftx` cells.

这是**最需要重点研究的一个**。它就是专门把 `$pmux` 转换成 `$shiftx`，内部维护一个 one-hot 数据库。它直接回答了一个关键问题：Yosys 认为什么情况下 `$pmux` 用移位器实现更省。

主要选项：
- `-min_density <percentage>` 移位器的最小密度，默认 50
- `-min_choices <int>` 控制信号的最小选择数，默认 3
- `-onehot ignore|pmux|shiftx` one-hot 控制信号的策略，默认 pmux
- `-norange` 禁用 range decoder 的 `$sub` 推断

同文件里还注册了 `onehot` pass。

### `opt_muxtree.cc`
官方说明：`opt_muxtree [selection]` — This pass analyzes the control signals for the multiplexer trees in the design and identifies inputs that can never be active. It then removes these dead branches from the multiplexer trees.

做的是 mux 树的死分支消除。注意它的限制：**只在完全选中的、不含 process 的模块上工作**。

### `muxcover.cc`
官方说明：`muxcover [options] [selection]` — Cover trees of `$_MUX_` cells with `$_MUX{4,8,16}_` cells.

把 `$_MUX_` 树覆盖成更宽的 mux 单元，是影响单元数量的关键 pass。

主要选项：
- `-mux4[=cost]`、`-mux8[=cost]`、`-mux16[=cost]` 指定覆盖用的 mux 类型和成本（默认 `$_MUX4_`、`$_MUX8_`、`$_MUX16_` 各有默认成本）
- `-mux2=cost` 覆盖决策时 `$_MUX_` 单元的成本
- `-dmux=cost` 解码器里用到的 `$_MUX_` 单元成本
- `-nodecode` 不插入解码器逻辑，减少可替换方案，但保证结果不会比原电路更差
- `-nopartial` 不考虑用 `$_MUX<N>_` 从少于 N 个信号中选择的映射

**这条的启示：** 单元数量的「成本模型」是可以调的。如果你们的目标是单元计数而非时序，调整 cost 参数本身就会改变结果——这既是机会（有调参空间）也是风险（说明 10% 可能靠调参就能拿到一部分，评审可能质疑创新性）。

### `pmuxtree.cc`
官方说明：`pmuxtree [selection]` — This pass transforms `$pmux` cells to trees of `$mux` cells.

`$pmux` 展开成 `$mux` 树，是反向操作，可作为对照。

### `opt_reduce.cc`
官方说明：`opt_reduce [selection]` — Executing OPT_REDUCE pass (consolidate `$*mux` and `$reduce_*` inputs).

合并 `$mux` 和 `$reduce_*` 的输入。

### `opt_share.cc`
官方说明：`opt_share [selection]` — Executing OPT_SHARE pass.

资源共享，把相同计算提取出来共用，间接减少单元数。

## 摸底实验该怎么设计

建议按这个顺序做对照实验，量化每个 pass 的贡献：

1. 先跑完整默认流程，记录 `stat` 输出的单元总数作为 baseline
2. 逐个禁用上述 pass（`opt_muxtree`、`pmux2shiftx`、`muxcover` 是最关键的三个），看单元数各涨多少——涨得越多说明这个 pass 吃掉的优化空间越大
3. 用 `write_rtlil` 导出优化前后的 RTLIL，对比差异，找出默认流程留下的「坏结构」
4. 统计 PMUX 相关单元在总数里的占比，估算理论上限

摸底结论直接决定打法：剩余空间 ≥15% 可以冲高分；只有 5% 左右就要重新评估这个选题。
